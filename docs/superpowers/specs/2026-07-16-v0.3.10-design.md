# v0.3.10 — GitHub sidebar: merge override, copy link, actioned PRs, Actions restructure, external links

Date: 2026-07-16
Status: approved, ready to plan

Five independent items shipping together in v0.3.10. Items 1–3 and 5 are contained;
item 4 (Actions restructure) touches `App.tsx`'s pane tree and carries the most risk.

---

## 1. Admin override merge

### Problem

`PrReviewView`'s "Merge…" button is always enabled and `merge_pr` runs a bare
`gh pr merge <n> --squash|--merge|--rebase`. When branch protection blocks the
merge, the user gets a raw error string and no path forward — even when they hold
admin rights and GitHub's own UI would offer a bypass.

### API findings (verified against the live GraphQL schema, 2026-07-16)

- `PullRequest.viewerCanMergeAsAdmin` exists and reflects **permission only** — it
  returns `true` even on a `CLEAN` PR. It is not a "can bypass right now" signal.
- `PullRequest.mergeStateStatus` exists, needs **no preview Accept header**, and
  resolves on the first query for open PRs.
- `mergeStateStatus` returns `UNKNOWN` for closed/merged PRs. This is expected and
  needs no retry loop — the merge dialog only opens on open PRs.
- `gh pr merge --admin` is the bypass flag ("Use administrator privileges to merge a
  pull request that does not meet requirements").

### Design

Backend `src-tauri/src/github/pr_review.rs`:

- `PrDetails` gains `merge_state_status: String` and `viewer_can_merge_as_admin: bool`.
  Both fields are added to the existing `DETAILS_QUERY` — **no extra round-trip**.
- `merge_pr(repo, number, method, admin: bool)` appends `--admin` when `admin` is true.
- `mod.rs`'s `merge_pr` command wrapper forwards the new arg.

Frontend `src/github/PrReviewView.tsx` — `MergeDialog` gains a reason line and a
conditional override checkbox, gated on `viewerCanMergeAsAdmin && mergeStateStatus`:

| `mergeStateStatus` | Behavior |
|---|---|
| `CLEAN` | No checkbox. Normal merge. |
| `BLOCKED` | Reason line + checkbox (if `viewerCanMergeAsAdmin`) |
| `BEHIND` | Reason line + checkbox (if `viewerCanMergeAsAdmin`) |
| `DIRTY` | Reason line "Resolve conflicts first". **No checkbox.** |
| `UNSTABLE` / `HAS_HOOKS` | No checkbox — a normal merge already succeeds |
| `UNKNOWN` | No checkbox — treat as normal merge |

The checkbox is unchecked by default, labelled "Merge without waiting for
requirements (admin override)", and passes `admin: true` when ticked.

**`DIRTY` is deliberately excluded.** `--admin` cannot bypass a merge conflict, so
offering the override there would produce a confusing failure.

Scope: review view only. PR inbox rows stay read-only.

## 2. Copy link

### Design

New `src/github/CopyLinkButton.tsx` — a small component owning its own
"copied" state: on click, `navigator.clipboard.writeText(url)`, swap the icon to a
checkmark for ~1.5s, then revert. `navigator.clipboard.writeText` is already the
established pattern (`src/sidebar/contextMenu.tsx:94`).

Call sites (**post-restructure placement — see item 4**, which moves run rows out of
the sidebar into the main tab):

- `PrReviewView` header, next to the new-window and GitHub icons —
  copies `https://github.com/{repo}/pull/{number}`.
- `RunsView` run rows (main tab), next to Cancel / Re-run —
  copies `https://github.com/{repo}/actions/runs/{id}`.
- `ActionsView` favorited run cards (sidebar, which keeps favorites) — same run URL.

Job rows are **out of scope** — the request was for the run URL.

Ordering note: item 4 relocates the run rows, so build item 4 first and add the run-row
copy button in its new home rather than adding it twice.

Both URLs are derived client-side (the same way `PrReviewView` already builds its
GitHub URL), so this item needs **no backend change**.

## 3. Actioned PR section

### Problem and finding

The original request assumed reviewed PRs linger in Team PRs. They do not.

Team PRs is built on `is:pr is:open review-requested:@me`, and GitHub drops a PR from
that search the moment you submit a review. Verified against the live account
(2026-07-16): 289 open PRs are `review-requested:@me`, every sampled one with
`viewerLatestReview = none`; 25 open PRs are `reviewed-by:@me -author:@me`; the
intersection of the two searches is **exactly 0**.

So reviewed PRs currently vanish from the inbox entirely. "Move them to a collapsed
section" therefore means **fetching PRs that are currently invisible**, not
re-bucketing the existing list.

The one place reviewed PRs *do* linger today is repo-filtered mode:
`list_github_repo_prs` returns every open PR in the repo, and `PrInboxView.tsx:259`
filters only on `author !== login`.

### Design

Backend `src-tauri/src/github/prs.rs`:

- `PR_FRAGMENT` gains `viewerLatestReview { state }` → `PullRequest.viewer_review_state:
  Option<String>`. The fragment is shared, so every existing query gets the field for free.
- New `list_actioned_prs(after)` running
  `is:pr is:open reviewed-by:@me -author:@me sort:updated-desc`, paginated with the
  existing `PrPage` / `collect_page` helpers, `first: 50`.
- New `list_github_actioned_prs` command in `mod.rs`.

Frontend `src/github/PrInboxView.tsx`:

- "Team Pull Requests" becomes two level-1 subsections:
  - **Needs Review** — today's `review-requested` list.
  - **Actioned** — the new list, `defaultOpen={false}`, with a "View more" when a
    cursor remains.
- Repo-filtered mode splits `repoPrs` into the same two subsections using
  `viewerReviewState` — no new network call.
- `PrRow` gains a chip showing the viewer's own review state when present
  (approved / changes requested / commented / dismissed).

**Membership rule:** Actioned holds the *entire* `reviewed-by:@me` result set,
including `COMMENTED` and `DISMISSED` — not just `APPROVED` / `CHANGES_REQUESTED`.
Reason: those PRs are absent from `review-requested` too, so a stricter rule would
leave them visible in no section at all. The account has real examples of both
(#1451 COMMENTED, #243 DISMISSED). The state chip disambiguates.

## 4. Actions restructure

### Goal

Actions moves from a single sidebar panel to a sidebar-navigates / tab-works split,
mirroring how PR review already opens as a main tab.

- **Sidebar** keeps the repo picker, favorites, and workflow list. It becomes navigation.
- **Main tab** shows one workflow's runs.
- **Right drawer** inside that tab shows the clicked run's jobs and the selected job's log.

### Precedent to follow

`PrReviewLeaf` (`App.tsx:143`) is the model: a pane-tree leaf kind
`{ kind: "prReview", id, repo, number }`, opened by `openPrReviewTab` (`App.tsx:1111`)
which dedupes against existing leaves and creates a tab titled `#123 · owner/repo`.

### Design

`src/App.tsx`:

- New `ActionsLeaf = { kind: "actions"; id: string; repo: string; workflowId: number;
  workflowName: string; focusRunId?: number }`, added to the `PaneLeaf` union with an
  `isActionsLeaf` guard.
- `openActionsTab(repo, workflowId, workflowName, focusRunId?)` mirrors `openPrReviewTab`:
  dedupe on `repo + workflowId`, else create a tab. Title: `{workflowName} · {repo}`.
  When the leaf already exists, focus it and update `focusRunId` in place.
- `focusRunId` preserves today's one-click-from-favorites-to-log. A fav card currently
  has a "Logs" button that jumps straight to the relevant job's log; without this the
  restructure would regress that to "open tab, find run, click it". `RunsView` opens the
  drawer for `focusRunId` on mount and whenever the prop changes.
- Every `node.kind === "prReview"` guard in the pane-tree helpers (lines 196, 258, 268,
  281, 361, 385, 1044, 1063, 1553, 1555, 1720–1722) must be audited for the new kind.
  An `actions` leaf has no `cwd`, exactly like `prReview`.
- **Not persisted across restart** — `migrateTab` drops `actions` roots, matching the
  existing `prReview` rule at `App.tsx:385`.

`src/github/ActionsView.tsx` (sidebar, shrinks):

- Keeps: repo picker, favorites, workflow list, the Run ▸ trigger button.
- Loses: the run list, the expanded jobs list, `showLog` / `openLog` / `openRunLog`,
  and the `onOpenPreview` prop.
- Workflow rows call `onOpenActionsTab(repo, wf.id, wf.name)` instead of expanding inline.
- Fav cards: the "Logs" button becomes `onOpenActionsTab(r.repo, r.workflowId, r.workflowName,
  r.id)` — same one-click-to-log outcome as today, now via the tab's drawer. The card keeps
  its status line and gains the item-2 copy button.

`src/github/RunsView.tsx` (new, main tab):

- Fetches `list_github_runs` for its `repo` + `workflowId`. Owns the run list, the
  Cancel / Re-run / Re-run failed actions, and the `CopyLinkButton` from item 2.
- Clicking a run opens the drawer for that run.

`RunDrawer` (inside `RunsView.tsx`):

- Right-side drawer, resizable via a divider, escape-to-close (reuse
  `useEscapeToClose` from `PrReviewView`).
- Top: the run's jobs via `list_github_jobs`. Auto-selects the failed job if any, else
  the first completed job — the same heuristic today's `openRunLog` uses.
- Below: the selected job's log text, with a per-`jobId` in-memory cache.
- Header carries an "Open in preview" button.

Backend `src-tauri/src/github/actions.rs`:

- `job_log` returns `JobLog { path: String, text: String, truncated: bool }` from its
  single existing fetch. It already holds the full text in memory and already writes
  the cache file at `dirs::cache_dir()/vector/logs/job-{id}.log`; it just returns both
  now. The drawer renders `text`; "Open in preview" passes `path` to the existing pane.
- `job_log_loading` and the `prepare_github_job_log` command are **deleted**. They exist
  solely because the preview pane needed a file path to open instantly on a placeholder;
  a drawer renders its own spinner.
- Log cap: 2 MB. Past that, keep the **tail** (CI failures are at the end) and set
  `truncated: true`; the drawer shows a truncation banner and points at "Open in
  preview" for the full file, which is written uncapped.

**Why "Open in preview" survives:** dropping it would regress search, syntax
highlighting, and pinning on logs — all capabilities the preview pane provides today.
The pane path also already handles oversized files
(`read_file_bytes` → `truncated` → `TooLargePlaceholder`).

## 5. External links open in the system browser

### Problem

`CommentBody` (`PrReviewView.tsx:38-41`) renders sanitized markdown through
`dangerouslySetInnerHTML` with no anchor handling. Clicking any link in any PR comment
navigates the WKWebView in place — Vector becomes a browser with no back button.
Greptile's "Fix in Claude" buttons are the most visible instance, but the bug is general.

`src/preview/MarkdownRenderer.tsx` has the identical flaw.

### Design

New shared hook `useExternalLinks(ref)` in `src/`:

- One delegated `click` handler on the container.
- `e.target.closest("a[href]")` → if the href scheme is `http:` or `https:`,
  `preventDefault()` and `invoke("open_path", { path: href })`.
- Non-http schemes are ignored and left to default handling. DOMPurify already strips
  `javascript:` hrefs; the scheme guard is defence in depth.

`open_path` (`main.rs:690`) already handles URLs — `PrReviewView`'s "Show PR in GitHub"
button uses it for `https://github.com/…`.

Wired into both `CommentBody` and `MarkdownRenderer`. One hook, two call sites, same
root cause.

## Verification

No test suite (per `CLAUDE.md`). Each item is verified by exercising it in a running
app (`npm run tauri dev`):

1. **Merge override** — open a `BLOCKED` PR: reason line + checkbox appear; merge with
   it ticked succeeds. Open a `CLEAN` PR: no checkbox. Open a `DIRTY` PR: no checkbox,
   conflict message shown.
2. **Copy link** — click copy in the PR header and on a run row; paste and confirm the
   URL; confirm the icon reverts after ~1.5s.
3. **Actioned section** — confirm Actioned is collapsed by default and populated
   (~25 PRs on this account); confirm state chips; confirm repo-filtered mode splits.
4. **Actions restructure** — click a workflow in the sidebar → tab opens; click the same
   workflow again → focuses the existing tab, no duplicate; click a run → drawer opens on
   the failed job's log; a fav card's Logs button → tab opens with that run's drawer
   already showing; "Open in preview" opens the full log; restart the app → actions
   tabs are gone (matching `prReview`). Also split an actions tab and drag it between
   tabs — the pane-tree guards are the risk area.
5. **External links** — click a Greptile "Fix in Claude" button and a plain link in a PR
   comment: both open in the system browser and the Vector window does not navigate.
   Repeat for a markdown file with a link in the preview pane.

## Risks

- **Item 4 is the risk.** It adds a leaf kind to the pane tree — every `prReview` guard
  in `App.tsx` is a place the new kind can be missed, and a missed guard means a crash
  or a broken split/drag. The audit list above is not optional.
- Items 1–3 and 5 are contained: one dialog, one button, one query + one section, one hook.
- Shipping all five together was an explicit user decision; the recommendation had been
  to split item 4 into its own release.
